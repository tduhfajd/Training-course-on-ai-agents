# Технический рабочий процесс

## Главная мысль

Техническая часть должна помогать думать, а не усложнять жизнь.

Базовый рабочий процесс:

1. Создать папку или репозиторий под задачу.
2. Вести исходные мысли и решения в Markdown.
3. Работать с агентом в Codex.
4. Смотреть структуру проекта в Cursor, VS Code или другой IDE.
5. Хранить историю в Git.
6. При необходимости генерировать PDF, DOCX, PPTX или другой внешний формат.

## Почему Markdown

Markdown хорошо подходит как основной формат, потому что он:

- легкий;
- читаемый;
- красиво отображается в репозитории;
- удобен для Git;
- понятен агентам;
- не привязан к конкретной программе;
- легко превращается в другие форматы.

Практическое правило:

```text
Markdown - источник смысла.
PDF, DOCX, PPTX и другие форматы - экспорт или упаковка результата.
```

## Когда нужен другой формат

Другой формат нужен, когда появляется внешняя задача:

- PDF - отправить финальный документ, сохранить верстку, распечатать;
- DOCX - передать человеку, который работает в Word;
- PPTX - выступить или отправить презентацию;
- HTML - опубликовать страницу;
- XLSX - передать таблицу в привычном офисном формате.

В этом случае можно попросить агента:

```text
Возьми материалы из Markdown-файлов проекта и подготовь версию в DOCX/PDF/PPTX. Сохрани структуру, убери рабочие заметки, оформи как документ для внешней аудитории.
```

## Codex, Cursor и VS Code

Один удобный режим:

- Codex - место, где идет диалог с агентом и выполняется работа;
- Cursor или VS Code - место, где удобно смотреть дерево файлов, читать материалы и вручную править текст;
- GitLab или GitHub - место, где хранится история и можно делиться проектом;
- NextCloud или NAS - место для больших файлов, документов, исходников и материалов.

Это не обязательный набор, а пример удобной связки. Главный принцип - задача должна жить в понятной файловой структуре.

## База знаний как основа будущего скила

Когда агент собирает базу знаний, она может стать сырьем для собственного скила.

Это особенно полезно, если:

- задача будет повторяться;
- есть устойчивый workflow;
- есть специфические правила;
- есть шаблоны;
- есть частые ошибки;
- есть полезные команды или scripts;
- хочется, чтобы агент в будущем быстрее входил в этот тип задач.

Но база знаний и скил - не одно и то же.

База знаний отвечает на вопрос:

```text
Что нужно знать по теме?
```

Скил отвечает на вопрос:

```text
Как агент должен действовать, когда возникает такая задача?
```

## Минимальная логика создания скила

1. Накопить опыт на 2-3 реальных задачах.
2. Выделить повторяемый процесс.
3. Собрать полезные правила, шаблоны и источники.
4. Решить, что должно лежать в `SKILL.md`, а что в `references/`, `scripts/` или `assets/`.
5. Попросить агента разработать скил.
6. Проверить скил на новой похожей задаче.
7. Улучшить по результатам проверки.

## Когда не нужен скил

Скил не нужен, если:

- задача одноразовая;
- информации мало;
- процесс еще неясен;
- достаточно обычного `knowledge-base/`;
- правила быстро меняются и пока не стабилизировались;
- создание скила займет больше времени, чем повторное объяснение агенту.
